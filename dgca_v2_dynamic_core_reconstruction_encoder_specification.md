## 0. First principles and the Zero-Semantics Transducer Contract

The Encoder is a **stateless, deterministic, context-invariant mechanical transducer** situated strictly outside the neural state $\mathcal{S}_t = (W_t, R_t, H_t^{slow})$. Its biological analogue is a peripheral sensory organ (e.g., retina or cochlea): it converts external physical stimuli (raw text strings) into standardized mechanical feature bundles without understanding, learning, or remembering.

### 0.1 Mandatory isolation invariants (`MUST / MUST NOT`)

1. **Zero Neural Visibility (`MUST NOT`):** The Encoder MUST NOT read, query, or depend on the structural graph $W_t$, working neural activity $R_t$, slow homeostasis $H_t^{slow}$, synapse strengths/evidence $(S, E)$, contextual owners (`OwnerID`), active Attractors, or `SurfaceReadoutLedgerV1` states.
2. **Zero Semantic Knowledge (`MUST NOT`):** The Encoder MUST NOT use pretrained tokenizers (e.g., BPE/WordPiece vocabularies learned from corpora), dense semantic embeddings, word IDs, part-of-speech tags, morphological dictionaries, or evaluator ground-truth labels (`A/B/C/D/E`).
3. **Strict Statelessness and Context-Invariance (`MUST`):** Identical normalized lexical surface tokens MUST produce byte-for-byte identical `(feature_text, support)` bundles regardless of event order $t$, surrounding words in the exposure, exposure ID, or execution mode (`LEARN`, `RETRIEVE`, `GENERATE`).
4. **Dual-Layer Separation (`MUST`):**
   - **Layer 1 (`Text-to-Bundle Transducer` — owned by this specification):** Segments a raw UTF-8 text stream into discrete ordered events and decomposes each event token into at most **4** mechanical orthographic features with fixed decimal `support` strings.
   - **Layer 2 (`SIC-V1 Projection Gate` — owned by `DGCA_CORE_RC4.md` §3.1):** Consumes the canonical `(feature_text, support)` bundle, merges duplicates, applies SHA-256 with fixed salts `s0..s3`, and projects supports onto LANGUAGE cells `8192..12287`.
5. **Direct Pass-Through Mode (`RAW_FEATURE_PASS_THROUGH`):** For unit-testing `SIC-V1` reference vectors (`FIFR-B04`: `"a"`, `"ab"`, `"é"`, `"f617"`), callers MAY bypass Layer 1 text segmentation and submit explicit `(feature_text, support)` pairs directly to Layer 2 (`Core` §3.1).

## 1. Stream normalization and temporal event segmentation

Natural language text consists of sentences/exposures, words/punctuation, and orthographic characters. The Encoder maps these three structural scales onto exposure boundaries, discrete time steps $t = 0, 1, \dots, n-1$, and synchronous spatial feature bundles.

### 1.1 Unicode normalization and validation

1. **UTF-8 and NFC:** Every raw input string MUST be validated as strict UTF-8 (reject lone surrogates, overlong encodings, and invalid byte sequences with `INVALID_ENCODER_INPUT`). Normalize the valid string to **Unicode Canonical Decomposition followed by Canonical Composition (`NFC`)** before any character indexing or slicing.
2. **Control character rejection:** Byte `0x00` (NUL) and ASCII control characters `0x01..0x1F` (except standard whitespace `\t`, `\n`, `\r`, and space `0x20`) are **forbidden** in caller-supplied natural text and MUST be rejected with `RESERVED_CONTROL_BYTE`. Byte `0x1F` (Unit Separator) is reserved exclusively for internal canonical markers (`EOS`) generated by the Encoder itself (§1.3).
3. **Whitespace collapsing:** Convert all sequences of one or more whitespace characters (`U+0020`, `\t`, `\r`, `\n`) into a single event-delimiter boundary. Strip leading and trailing whitespace before segmentation. Empty strings after stripping yield `EMPTY_EXPOSURE_INPUT`.

### 1.2 Lexical vs punctuation segmentation rules

Scan the NFC-normalized string by Unicode scalar values (code points) from left to right:

1. **Contiguous lexical tokens:** Any maximal contiguous run of characters that are neither whitespace nor punctuation delimiters forms one lexical token $w$.
2. **Internal punctuation delimiters (separate non-terminal events):** Each occurrence of `,`, `،` (`U+060C`), `;`, `؛` (`U+061B`), `:` is detached as its own independent event token $w$ of length $L=1$, with `marker = NONE`.
3. **Terminal sentence delimiters (`EOS` trigger):** One or more consecutive occurrences of `.`, `!`, `?`, `؟` (`U+061F`) at the end of a sentence or clause detach and emit a single canonical **`EOS` event** (§1.3) rather than a raw punctuation word. If an exposure input is marked `append_eos = true` (LAB DEFAULT for complete sentence exposures in G1/G2), the Encoder appends a single canonical `EOS` event at the end of the event list if one was not already emitted by terminal punctuation.
4. **Exposure-start boundary flag:** Event $t = 0$ of any independent exposure (`BEGIN_EXPOSURE`) is assigned `boundary = true` (`HARD_BOUNDARY`). Subsequent events $t = 1 \dots n-1$ within the same contiguous sentence have `boundary = false`.

### 1.3 Canonical `EOS` lexical event representation

In accordance with `DGCA_CORE_RC4.md` (§9.3, §9.4) and `DGCA_LLA_RC4.md` (§7.1), `EOS` is an explicit learnable terminal lexical event—**not** an unlearned `HARD_BOUNDARY` reset. When an `EOS` event is emitted at step $t$:

- **Peripheral envelope fields:** `raw_surface = "<EOS>"`, `marker = EOS`, `salience = "1.000000"`, `boundary = false` (cannot be event 0 alone; a bare `EOS` exposure is rejected as `EMPTY_LEXICAL_EXPOSURE`).
- **Reserved mechanical feature bundle (collision-free):** Because `0x1F` is rejected from user text (§1.1), the `EOS` feature bundle uses the reserved `0x1F` prefix and cannot collide with any natural word:

| Feature role | `feature_text` (ASCII / UTF-8 bytes) | `support` | Quantized `u` (millionths) |
|---|---|---:|---:|
| `EOS_F0` | `"\x1fEOS#0"` (`1f 45 4f 53 23 30`) | `"1.000000"` | `1_000_000` |
| `EOS_F1` | `"\x1fEOS#1"` (`1f 45 4f 53 23 31`) | `"0.900000"` | `900_000` |
| `EOS_F2` | `"\x1fEOS#2"` (`1f 45 4f 53 23 32`) | `"0.800000"` | `800_000` |

This 3-feature bundle activates up to $3 \times 4 = 12$ cells in `LANGUAGE`, enabling the network to form and consolidate a dedicated native `EOS` Assembly (`K_min = 3..12`) and attest it in `SurfaceReadoutLedgerV1` with `marker = EOS`.

## 2. Deterministic 4-Feature Orthographic Decomposition

To satisfy the mathematical invariants of `DGCA_CORE_RC4.md` and `DGCA_LLA_RC4.md`, word decomposition obeys a hard ceiling of **`MAX_FEATURES_PER_EVENT = 4`** unique features per event.

### 2.1 Architectural rationale for the 4-feature ceiling and 4-tier support scale

1. **Exact alignment with Assembly capacity (`K_max = 16`):** Each feature projects via `SIC-V1` (`4` salts) onto at most `4` distinct cells in `LANGUAGE`. Therefore, `4` features stimulate at most $4 \times 4 = 16$ cells per event—matching `K_max = 16` (`Core` §2.0, §12). A single word's neural footprint fits completely inside a single Assembly without spillover, ensuring `CoreCoverage(A, t) >= rho_core = 0.70` upon word recurrence.
2. **Guaranteed compliance with `ANCHOR_SOURCE_MAX = 64`:** Because a single event activates $\le 16$ cells, the union of two qualifying owned examples in `AnchorSourceSet` (`Core` §5.2, §7.3) contains at most $32 \le 64$ cells, eliminating `ANCHOR_CONTEXT_TOO_WIDE` failures.
3. **Unbroken triangle formation (`FORM` in `Core` §2.0):** By assigning the full bounded word identity `F0` the unique maximum support `"1.000000"`, its projected cells achieve the highest Pass-2 activity $A_j^+$ and deterministically win the top `6 co-active intra` latent slots of one another (`Core` §1.3), forming the required reciprocal consolidated `LOCAL` triangle (`d >= 2, D >= 0.70`).
4. **High inter-word separation ($d_P, d_Y \ge 0.40$ and $m_P = 0.05$):** Excluding bare single-character boundary features (`^c` or `c$`) prevents false overlap between distinct words that share only initial/final letters (e.g., `"كتب"` vs `"كسب"` or `"cat"` vs `"cut"`).

### 2.2 Decomposition algorithm for a normalized lexical token $w$

Let $w = c_0 c_1 \dots c_{L-1}$ be a non-empty NFC-normalized lexical or internal-punctuation token consisting of $L \ge 1$ Unicode scalar values (code points). Reserve the prefix characters `^` (`0x5E`), `$` (`0x24`), and `~` (`0x7E`) as structural framing markers:

- If $w$ has UTF-8 byte length $> 64$ bytes, reject with `TOKEN_TOO_LONG` (first-lab tokens MUST be $\le 64$ UTF-8 bytes so that all generated features are strictly $\le 68 \ll 4096$ bytes per `Core` §3.1).

Extract up to **four** raw candidate features $(f_k, s_k)$ according to token length $L$ in code points:

| Tier | Feature ID | Condition | Construction rule (Unicode code points) | Fixed `support` string | `Q6` integer support |
|---|---|---|---|---:|---:|
| **Tier 0** | `F0` (Full Lexical Identity) | Always ($L \ge 1$) | `"^" + w + "$"` | `"1.000000"` | `1_000_000` |
| **Tier 1** | `F1` (Prefix Digram) | $L \ge 2$ | `"^" + c_0 c_1` | `"0.900000"` | `900_000` |
| **Tier 2** | `F2` (Suffix Digram) | $L \ge 2$ | `c_{L-2} c_{L-1} + "$"` | `"0.800000"` | `800_000` |
| **Tier 3** | `F3` (Medial Trigram / Core) | $L \ge 3$ | `"~" + c_m c_{m+1} c_{m+2}`, where $m = \lfloor (L - 3) / 2 \rfloor$ | `"0.750000"` | `750_000` |

#### Special handling for short tokens ($L = 1$ and $L = 2$) to ensure `K_min >= 3` cells:
A single feature (`F0` alone for $L=1$) projects to 4 indices, which in the rare case of a self-collision across salts (`4096` modulo reduction) might yield only 3 or fewer cells, or leave too few distinct sources for 2/2/2 role selection (`Core` §7.3 requires $\ge 2$ distinct sources per role). Therefore:
- **When $L = 1$ (e.g., `"a"`, `"و"`, `","`):** In addition to `F0 = "^" + c_0 + "$"` (`"1.000000"`), emit `F1 = "^1:" + c_0` (`"0.900000"`) and `F2 = "1$:" + c_0` (`"0.800000"`). This guarantees 3 distinct features (up to 12 cells) for every single-character token.
- **When $L = 2$ (e.g., `"ab"`, `"في"`):** `F0 = "^" + c_0 c_1 + "$"` (`"1.000000"`), `F1 = "^" + c_0 c_1` (`"0.900000"`), and `F2 = c_0 c_1 + "$"` (`"0.800000"`) are already 3 distinct strings; `F3` is omitted.

### 2.3 Canonical sorting and bundle finalization

After extracting the raw candidate pairs for event $t$:
1. Encode each `feature_text` in strict UTF-8 (already NFC).
2. Because `F0, F1, F2, F3` use distinct structural framing (`^...$`, `^..`, `..$`, `~...` or `^1:`/`1$:`), they are guaranteed to be **pairwise distinct byte strings** for every token $w$; if a custom caller pass-through ever supplies duplicate feature bytes, merge them by exact decimal Noisy-OR and half-even rounding as mandated by `Core` §3.1.
3. Sort the feature list in **strictly ascending unsigned UTF-8 byte order** (`Core` §3.1).
4. Compute `feature_bundle_digest`: the SHA-256 digest of the canonical serialized feature bundle:
   ```text
   ASCII("DGCA-BUNDLE-V1") || 0x00 || salience_millionths_u32_BE || feature_count_u32_BE
   || for each sorted feature: (byte_length_u32_BE || feature_UTF8_bytes || support_millionths_u32_BE)
   ```

## 3. Mathematical verification against `Core RC4` and `LLA RC4`

Under `LANGUAGE` regional parameters ($\delta_A = 0.20, \gamma_A = 0.80, \beta = 0.80, \theta_{active}^{init} = 0.20, \theta_{emit} = 0.23, g_j = 1.00$):

1. **Pass-1 and Pass-2 Activity vs Creation Gate ($\theta_{create} = 0.20$):**
   - For a cold event ($A(t-1) = 0, P_T = 0, \sigma = 0$), a single feature in a microcolumn ($\overline{\hat{D}}^{(1)}_{col} = X_j / 8$) produces normalized Pass-1 drive:
     $$D_j^{(1)} = \frac{X_j}{1 + 0.80 \times (X_j / 8)} = \frac{X_j}{1 + 0.10 X_j}$$
   - For the lowest tier (`F3`, $X_j = 0.75$):
     $$D_j^{(1)} = \frac{0.75}{1.075} \approx 0.697674 \implies A_j^{(1)} = 0.80 \times 0.697674 \approx 0.55814 \ge \theta_{emit} = 0.23$$
   - For the highest tier (`F0`, $X_j = 1.00$):
     $$D_j^{(1)} = \frac{1.00}{1.10} \approx 0.909091 \implies A_j^{(1)} = 0.80 \times 0.909091 \approx 0.72727 \ge \theta_{emit} = 0.23$$
   - Consequently, **all 4 tiers** reliably enter the Pass-1 emission frontier $E_t^{(1)}$ and produce final Pass-2 activity $A_j^+ \ge 0.558$. Their pairwise creation coactivity is at least $0.55814 \times 0.55814 \approx 0.3115 \ge \theta_{create} = 0.20$ (passing even the historical `0.30` comparator!).
2. **Orthographic Contrast Distance ($d_P, d_Y \ge 0.40$) on Minimal Pairs:**
   - Consider two minimally different 3-letter words sharing 2 out of 3 letters in the same positions: $w_1 = \text{"كتب"}$ and $w_2 = \text{"كسب"}$.
   - Decomposition of `"كتب"`: `F0 = "^كتب$"`, `F1 = "^كت"`, `F2 = "تب$"`, `F3 = "~كتب"`.
   - Decomposition of `"كسب"`: `F0 = "^كسب$"`, `F1 = "^كس"`, `F2 = "سب$"`, `F3 = "~كسب"`.
   - **Number of shared features: ZERO (`0 / 4`)!** Except for accidental modulo-4096 hash collisions across the 4096 region cells, the two words have nearly disjoint neural footprints ($d(U,V) > 0.85 \gg 0.40$), guaranteeing both branch discovery (`nu_ctx >= 0.30`) and P-pair physical margin ($L_z - U_z \ge 50,000$).
   - Even for 4-letter words sharing both prefix and suffix digrams (e.g., $w_1 = \text{"كتبت"}$ vs $w_2 = \text{"كسبت"}$ where `F1 = "^كت"` differs, or $w_1 = \text{"مكتب"}$ vs $w_2 = \text{"مكسب"`} sharing `F1 = "^مك"`), `F0`, `F2`, and `F3` remain completely distinct (`3 / 4` distinct features, weight ratio $2.55 / 3.45 \approx 0.74 \ge 0.40$).

## 4. Dual Envelope Protocol: Core Input vs Peripheral Readout Ledger

To enforce the `ZERO_SELECTION_LEAKAGE` invariant (`DGCA_CORE_RC4.md` §9.4), the Encoder splits each segmented event $t$ into **two strictly segregated structures**:

```text
EncodedEventEnvelopeV1 {
  // 1. Core Neural Payload (passed to Core EVENT / READ_ONLY / GENERATE prompt)
  core_event: {
    exposure_id: u64 | NONE,
    event_order: u32,
    modality: LANGUAGE (0x02),
    origin: EXTERNAL_DIRECT | READ_ONLY_OBSERVED | INTERNAL_SELECTED,
    boundary: bool,
    salience: "1.000000",
    features: sorted list of (feature_text_NFC_UTF8, support_decimal_6), // max 4 items
    feature_bundle_digest: bytes32
  },

  // 2. Peripheral Readout Envelope (held in I/O shell; NEVER read by Core/LLA ranking)
  peripheral_surface: {
    raw_surface_NFC_UTF8: string,      // e.g., "كتب" or "<EOS>"
    surface_sha256: bytes32,
    feature_bundle_digest: bytes32,    // must match core_event.feature_bundle_digest
    canonical_features_copy: sorted list of (feature_text_NFC_UTF8, support_decimal_6),
    marker: NONE (0x00) | EOS (0x01)
  }
}
```

### 4.1 Closed-loop feedback during `GENERATE_EPISODE` (`Core` §9.3)

1. During `LEARN`, the I/O shell sends `core_event` to `Core`, and holds `peripheral_surface` in the peripheral outbox listener so that at `END_EXPOSURE` any pre-existing live Assembly meeting `CoreCoverage >= 0.70` and `M_A^fresh >= 0.40` can record an attestation for `(AssemblyID, generation, raw_surface_NFC_UTF8, feature_bundle_digest, marker)` in `SurfaceReadoutLedgerV1`.
2. During `GENERATE_EPISODE`, after `Core` §9.2 (`FULL vs CONTROL`) selects a winning `(AssemblyID, generation)` purely by neural `score_next(G)`, `ResolveReadout` retrieves the attested `peripheral_surface` record from `SurfaceReadoutLedgerV1`.
3. If `marker == EOS`, generation halts with `GEN_STOP_EOS`. Otherwise, the peripheral shell takes `canonical_features_copy` from the ledger row **without re-running text segmentation**, wraps it in a new `core_event` with `origin = INTERNAL_SELECTED`, and feeds it to `Core` §9.3 for step $t+1$ (which applies `P_T_debit_selected` and advances the rollout).

### 5.1 Canonical decomposition and `SIC-V1` projection reference vectors

All implementations MUST reproduce the following exact decomposition and `LANGUAGE` (`region_u8 = 0x02`, base global offset `8192`) cell indices under `SIC-V1` (`Core` §3.1):

1. **Single-character token `w = "a"` ($L = 1$):**
   - Extracted features (sorted by unsigned UTF-8 byte order):
     1. `("1$:a", "0.800000")` (`hex: 31 24 3a 61`, `u = 800000`)
     2. `("^1:a", "0.900000")` (`hex: 5e 31 3a 61`, `u = 900000`)
     3. `("^a$", "1.000000")` (`hex: 5e 61 24`, `u = 1000000`)

   - Extracted features (sorted by unsigned UTF-8 byte order):
